# svett.app

svett is an iPhone app for lifting and cardio. It has one feed for every kind of workout. Users can export all their data and import it back. A coach runs on the user's own ChatGPT plan after **Continue with ChatGPT**.

`docs/plan.html` is the approved build plan. Read it before you change anything. It names every pull request, its proof, and the rules the code keeps.

## Machines

| Machine               | Job                                                                                                                                       |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| rena-devbox (Linux)   | Main working copy. Agents, package installs, type checks, lint, unit tests, and the phase 6 server.                                       |
| rena-devbook (Mac)    | Native iOS builds, the Metro dev server for the simulator, and the iPhone 16 Pro Max simulator.                                           |
| rena (Mac laptop)     | Real-phone work through iPhone Mirroring, only when a task needs the phone.                                                               |
| GitHub hosted runners | Lint, type checks, tests, an iOS compile check, and the release job after each merge. Never add a self-hosted runner: the repo is public. |

## Rules

- Every pull request goes through the sol loop and then the council. It merges only when both council reviewers score it 9 or higher.
- Phone sessions are read-only unless the task says otherwise. Do not sign in or out, buy, start trials, post, like, follow, comment, or save or delete any workout or activity.
- Never commit `research/screenshots/`, real names, email addresses, IP addresses, user names, tokens or a real Hevy export.
- `research/features.md` is the Hevy and Strava feature inventory the plan is based on.

## Develop

Node and pnpm versions are pinned in `.node-version` and `packageManager`. On rena-devbox, Node 26 comes from fnm. Put it on the path with `eval "$(fnm env)" && fnm use` before running anything.

On rena-devbox:

```sh
pnpm install
pnpm lint
pnpm typecheck
pnpm test
pnpm fmt
```

`pnpm --filter @svett/mobile exec expo export --platform ios` bundles the app's JavaScript. It proves the app bundles without a Mac.

`devbook-build.sh` syncs `~/svett-app` to the branch, installs packages, builds the app for the simulator, installs it and opens it. It signs the simulator app to run locally, with no team, so the app carries its entitlements. The Keychain and Apple Health refuse an app without them. Metro's log is `~/svett-app/metro.log`. The first run needs the clone, so run it from a copy of the script or clone the repo to `~/svett-app` first. After each install it marks svett's first-run pages seen, so they never cover the tabs a proof script presses. A launch with `-svettFirstRun show` opens them anyway, and `-svettFirstRun skip` passes them and remembers that.

`SVETT_METRO` is the one Metro address setting, `localhost:8081` by default. A host with no port means port 8081. `devbook-build.sh`, `sim/tabs.sh` and `sim/launch.sh` all open a Debug build on it. When its host is `localhost`, `devbook-build.sh` starts Metro on that port first. Otherwise it expects Metro already running there.

Agents on the Mac run in non-interactive shells that skip `~/.zshrc`. When `fnm` or `pod` is not on `PATH`, `devbook-build.sh` also looks in `~/.local/share/fnm/` and in the newest `~/.local/share/mise/installs/ruby/*/bin/`.

The native build runs only when needed. The script compares the Expo fingerprint of the native inputs with the one saved after the last successful build in `~/svett-app-build/<configuration>/`, which also holds the build output. When they match, a Debug run skips `expo prebuild`, `pod install` and `xcodebuild`, and goes straight to installing and starting Metro. Otherwise `expo prebuild` and `pod install` run only when `apps/mobile/ios` was generated from other native inputs, which it records in `apps/mobile/ios/.svett-fingerprint`. A Release run always runs `xcodebuild` to embed the current JavaScript. The script prints which path it took. Pass `--native` to force the full build.

The scripts use the simulator named by `SVETT_SIMULATOR`, by default a dedicated `svett iPhone 16 Pro Max` on iOS 27. `devbook-build.sh` creates it when it is missing. Names match exactly, so the stock `iPhone 16 Pro Max` is never picked by accident.

`sim/tabs.sh` drives the simulator with `agent-device`. It opens the app, taps each of the five tabs, and saves numbered screenshots to `out-dir`, by default `~/svett-proof/<branch>/`. Pass `--release` after a Release build so it opens the app without Metro.

`sim/launch.sh` relaunches the app and passes each extra argument to the app process, for example `sim/launch.sh -svettFixture /path/to/fixture.json`. Pass `--release` after a Release build. It leaves the app running.

`sim/gallery.sh` opens the design gallery twice, at the default and at the largest accessibility text size. Each pass saves a screenshot per page until the gallery's end marker is on screen, then one of the open sheet, as `<pass>-NN.png` and `<pass>-sheet.png` in `out-dir`, by default `~/svett-proof/<branch>/gallery/`. It sets the text size with `agent-device settings text-size`, and leaves the simulator at the default size. It reaches the gallery and the sheet through the `svett://gallery` and `svett://gallery?sheet=open` links, because agent-device 0.21.37 refuses taps in screen content on iOS 27. It reads UIKit's touch-transparent floating bar containers as toolbars covering the screen. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`.

`sim/checks.sh` runs every phone check on the simulator. It opens Phone checks from the You tab and resets the checks. It relaunches and reopens Phone checks for the Keychain check. It grants notifications ahead, presses Run on the notification check and goes to the Home Screen in the next call, because the notification is due 10 seconds later. It waits there for the banner and comes back. It runs Apple Health and allows the sheet when it shows. It moves the simulator along a route with `simctl location` and keeps svett in the background for 70 seconds for GPS. It opens the ChatGPT sign-in sheet and cancels it. After each step that leaves svett it opens svett again without a relaunch, reopens Phone checks from the You tab when svett comes back elsewhere, and stops with an error before any scroll or press while svett is not in front. Last it relaunches, copies the report and saves the clipboard as `report.txt`, with a note that GPS ran on the Home Screen because the simulator cannot lock. A Debug report also notes that a development client reload forgets when svett was away. Numbered screenshots and the report go to `out-dir`, by default `~/svett-proof/<branch>/checks/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`. agent-device 0.21.37 refuses a selector press inside screen content on iOS 27 as covered, because it reads UIKit's touch-transparent floating bar containers as toolbars over the screen. A press at coordinates skips that check, so the script reads an element's frame with `agent-device get attrs` and presses its centre.

`sim/cardio.sh` records a run along `scripts/sim/cardio-route.json`, a 2.4 km route in two legs. At the largest text size it opens svett, grants it location, which agent-device does only for an open app, and relaunches it. Then it opens Record through `svett://record` and starts a run at the route's first waypoint. When Start fails, it prints the reason the Record screen shows above Start, word for word. The simulator plays the first leg with `simctl location` while svett sits on the Home Screen, the stand-in for a locked screen. Back in svett it pauses, resumes, plays the second leg, pauses and finishes, then screenshots every page of the saved activity. Last it reads the activity from the app's database with `scripts/cardio-proof.ts check` and writes `proof.txt`. It fails unless the saved distance is within 1% of the route's length and the splits add up to the distance and the moving time. Output goes to `out-dir`, by default `~/svett-proof/<branch>/cardio/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/checks.sh`. `svett://activity/<id>` opens a saved activity.
`sim/chatgpt.sh` first runs `scripts/chatgpt-tests.sh`, which runs `swift test` on the ChatGPT sign-in's Swift package and saves the output as `swift-test.txt`. Then, at the largest text size, it relaunches svett with each `-svettChatGPTStub` scenario, opens the ChatGPT settings through `svett://chatgpt` and walks every state against the stand-in for OpenAI. It fails when a state or message it expects does not show. `--live` instead waits up to 10 minutes for a person to sign in with a real account, then signs out. Screenshots go to `out-dir`, by default `~/svett-proof/<branch>/chatgpt/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`.

`sim/exercises.sh` proves the exercise library at the largest text size. It opens `svett://exercises?q=barbell%20squat`, checks the first result is Barbell Squat and opens it. It opens `svett://exercises/new` filled with a name unique to the run, presses Save and checks the detail says Custom. Then it relaunches, searches for that name and opens it again. It fails when a screen, the expected first result or the saved exercise is missing. `SVETT_EXERCISE_NAME` sets the name. Numbered screenshots go to `out-dir`, by default `~/svett-proof/<branch>/exercises/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`, and presses rows and buttons at their centre like `sim/checks.sh`.

`sim/progress.sh` generates the 300-workout fixture, copies it into the app's data container and relaunches svett on it at the largest text size. It checks the Progress tab shows 300 workouts, then opens each chart screen through its link: `svett://progress/exercise/<exercise id>?range=all` for bench press, `svett://progress/muscles?week=2026-10-26` for the fixture's last full week, and `svett://progress/measurements?kind=body_weight&range=all`, then the same with `&sheet=open` for the add sheet. It shoots each screen a page at a time until the screen's closing rule is on screen, and fails when a chart was on none of the pages. Screenshots go to `out-dir`, by default `~/svett-proof/<branch>/progress/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`.

`sim/history.sh` proves the Progress screens on the 300-workout fixture at the largest text size. It generates the fixture, copies it into the app's data container and relaunches on it. It scrolls the history list until the oldest workout's row is on screen, and fails when a screen shows no row or after 600 screens. It opens the newest workout through `svett://workout/<id>`, edits its first normal set through `svett://workout/<id>/set/<set id>` to 222.5 kg on the keypad, and fails unless the detail shows the new weight. Then it saves the workout as a routine, deletes it, checks the count reads 299, presses Undo and checks it reads 300 again. Last it opens `svett://calendar?month=2026-10`. Numbered screenshots go to `out-dir`, by default `~/svett-proof/<branch>/history/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`, and presses screen content at an element's centre like `sim/checks.sh`. `svett://progress` opens the Progress tab.

`sim/walkthrough.sh` records svett with agent-device's `record start` while it walks every tab and the main screens on a fresh copy of the 300-workout fixture, once at the default text size and once at the largest. Each pass relaunches with the ChatGPT stand-in signed in and `-svettFirstRun show`, takes each first-run page and presses Next until it ends on Train. Then it opens Train, a routine, the library, Record, Home, Progress, the newest workout, bench press's chart, the calendar, muscles, measurements, Coach, ChatGPT, the You tab, Your data, Units and plates and Account, through their links and the You tab's button. It saves `default.mp4`, `largest.mp4` and `<pass>-NN-<stop>.png` in `out-dir`, by default `~/svett-proof/<branch>/walkthrough/`, and fails when a screen does not show.

`sim/speed.sh` measures the plan's five speed targets. It runs `sim/startup.sh`, `sim/logger.sh` and `sim/history.sh`, then imports a 300-workout Hevy export that `node scripts/hevy-export.ts` writes, on a new database, and asks the coach's stand-in question. With `-svettTiming 1` the import result and the coach show the times svett measured itself, and the script reads them. It writes `speed.md` with What, Target, Measured, Build and Device for each target, and the folder of each step, in `out-dir`, by default `~/svett-proof/<branch>/speed/`. A step that fails says so in its row, and the script exits 1. `SVETT_SPEED_SCRIPTS` names another folder for the three scripts it runs. `docs/speed.md` explains each measurement and holds the last table.

`sim/headers.sh` proves the large titles at the largest text size, on the 300-workout fixture. It generates the fixture and copies it into the app's data container as `sim/progress.sh` does, so every screen has real content under its title whatever an earlier run left there. It relaunches svett on it, presses the Home, Train, Progress and You tabs, then opens `svett://exercises`, `svett://data` and `svett://gallery`. It checks the Progress tab counts 300 workouts and the Train tab lists the routines. It shoots each screen at rest, scrolls it down 60% of the screen so content sits under the collapsed title, and shoots it again. Coach comes last, because its keyboard covers the tab bar. svett relaunches signed in on the stand-ins, `-svettChatGPTStub signedIn` and `-svettCoachStub` with `coach-best-squat.json`, and asks three questions through `svett://coach?ask=...`, so the chat is longer than the screen. At the largest text size the composer fills the bottom of the screen, where `scroll` starts its swipe, so the chat moves only by `gesture pan` inside the lower part of its frame, read from `get attrs` each time. It shoots the chat from the top with the title expanded and dragged with the title collapsed, each once two reads of New chat's frame agree, then presses the question field, types a few characters, and shoots the composer above the keyboard with the latest answer above it. It fails when a screen does not show, when the fixture did not open, when Train, Progress, You, Exercises, Your data, the gallery or the chat looks the same after the scroll, when the chat fits on the screen, or when the field did not take the text, the composer did not rise above the keyboard or the latest answer is not above it. Home is shorter than the phone, so it need not move. It presses the field and starts each drag only clear of the bottom edge, and presses once two reads of its frame agree. Numbered screenshots go to `out-dir`, by default `~/svett-proof/<branch>/headers/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`.

`sim/coach.sh` runs the Swift tests too, then copies the 300-workout fixture and the coach's stand-in fixtures into the app's data container. At the largest text size it relaunches svett once per state and asks through `svett://coach?ask=...`: signed out, no plan usage, "What was my best squat set last month?" answered by `-svettCoachStub` from `packages/tools/fixtures/coach-best-squat.json` while the read tools run on the fixture, and the plan's limit from `coach-plan-limit.json`. It fails when the answer, the data it read or the plan's wording does not show. `--live` asks OpenAI with a real account and `-svettCoachRecord`, signing in first when needed, and saves the exchange as `coach-live.json` in `out-dir`, by default `~/svett-proof/<branch>/coach/`. Copied over `coach-best-squat.json`, it becomes the stand-in that `pnpm test` replays. `pnpm coach-stand-in` rebuilds every stand-in from OpenAI's documented stream events.

`sim/proposals.sh` copies the fixture and the three proposal stand-ins, `coach-propose-routine.json`, `coach-propose-program.json` and `coach-propose-malformed.json`, into the app's data container. At the largest text size it relaunches svett on each and asks its question through `svett://coach?ask=...`. For the routine and the three-routine program it checks the Train tab does not list them, opens the preview from the card's Preview button, presses Apply in the header, finds every routine and the folder on the Train tab, presses Undo and checks they are gone. For the malformed routine it checks the chat says why svett refused it and shows no card. It presses an element only once two reads of its frame agree and only above the home indicator. Screenshots go to `out-dir`, by default `~/svett-proof/<branch>/proposals/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`. `svett://proposal/<id>` opens a proposal's preview.
`sim/routines.sh` proves routines at the largest text size, on the 300-workout fixture. It generates the fixture and copies it into the app's data container as `sim/progress.sh` does, and every relaunch opens it. Set `SVETT_FIXTURE` to a fixture's path already in the data container to use that one instead. It discards a workout an earlier run left in progress and goes back to the Train tab. It opens `svett://routines/new` with a name unique to the run, adds Barbell Squat through `svett://routines/new/exercises?q=barbell%20squat`, types 60 kg for 8 to 12 reps on the keypad and adds two sets that copy it. It saves, relaunches, opens the routine from the Train tab and starts it. It checks the workout in progress holds all three sets with that target, and that the Train tab shows the workout. It fails when a screen, the exercise, a target or a set is missing. `SVETT_ROUTINE_NAME` sets the name. It saves `cold-start.txt` with four lines. The first is the time from a relaunch until the Train tab lists the routines, an upper bound because it includes agent-device's calls. The second times the same calls against the running app, the automation's own share. The third is their difference, also an upper bound, because it still includes the script's wait before it opens the Train tab. The fourth is the time svett measured itself, which the Train tab shows when the app is launched with `-svettTiming 1`. It runs from the start of the process, or from main() when iOS prewarmed the launch, to the first frame with the routine list, and lists each step on the way, such as the database open and the routines read. Here it includes the wait for the `svett://train` link, so the plan's 2 second target judges `sim/startup.sh`'s time instead. Numbered screenshots go to `out-dir`, by default `~/svett-proof/<branch>/routines/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`, and presses at an element's centre like `sim/checks.sh`.

`sim/startup.sh` times the cold start alone. At the largest text size it relaunches svett 5 times on the 300-workout fixture with `-svettTiming 1` and `-svettLink svett://train`, so each launch opens straight into the Train tab. The routine list starts below the screen at that size, so the script waits without moving the screen until Start empty workout or the workout in progress shows, which svett draws with the list. Then it scrolls down to the list and to the time below it, and saves the time as `launch-<n>.txt`. That time runs from the process start, or main() for a prewarmed launch, to the first frame with the routine list, with nothing taken off, so database work that finishes after the first screen still counts. The plan's 2 second target judges its median on a Release build. `startup.txt` lists every step of every launch, then the median of the time and of each step. It fails when a launch did not open straight into the Train tab or its Train tab never listed the routines. A build from main before the launch marks ignores `-svettLink`, so the script opens `svett://train` for it and says its time includes that wait. `SVETT_LAUNCHES` sets the number of launches, and `SVETT_FIXTURE` works as in `sim/routines.sh`. Screenshots and the report go to `out-dir`, by default `~/svett-proof/<branch>/startup/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`.

The steps of a launch come from three places. The kernel's start of the process and `ActivePrewarm` come from SvettNative. The config plugin `apps/mobile/plugins/launch-marks.ts` makes Expo's generated AppDelegate record main() and the start and end of didFinishLaunching in `LaunchMarks`, and it stops the prebuild when the template changed shape or the file holds only some of the marks. React Native's `performance.rnStartupTiming` gives the start and end of the bundle. JavaScript records its own start, the database steps, the first screen, the Train tab and the routine list in `apps/mobile/src/data/launch-timing.ts`. iOS may prewarm svett, running the process up to main() long before a tap, so a launch with `ActivePrewarm` set is timed from main(). The pure rules are in `packages/core/src/cold-start.ts`.

`sim/logger.sh` proves the logger at the largest text size, on a fresh copy of the 300-workout fixture in the app's data container, `Documents/svett-logger.db`. It launches with `-svettTiming 1`, which makes the workout screen show how long the last set took to show done. It starts the fixture's Legs routine, types sets on the keypad, changes a set type, adds a set, moves an exercise, and adds Plank through `svett://train/workout/exercises?q=plank`. Then it kills svett with `xcrun simctl terminate`, launches it again, opens the workout from the bar above the tabs and checks every set came back. It finishes the workout, starts an empty one from the Train tab, and marks a set done that takes last time's values. After the restore and after each finish it copies the database file with its write-ahead log and checks the workout's rows with `node scripts/workout-rows.ts`. It saves the time a set took to show done as `set-done.txt`. Only a Release build's time counts against the 100 millisecond target. It fails when a screen, a set, a value or a row is missing. Numbered screenshots go to `out-dir`, by default `~/svett-proof/<branch>/logger/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`. It needs the simulator's UDID for `simctl`, which only finds the data container and kills svett.

`sim/tools.sh` proves the logger tools at the largest text size, on a fresh copy of the 300-workout fixture in `Documents/svett-tools.db`. It grants notifications ahead, switches weights to pounds through `svett://settings/workout`, starts an empty workout and adds Barbell Squat and Romanian Deadlift. It sets the squat's rest to 0:30 from the exercise's options, types 225 lb for 5 and marks the set done. In the very next call it goes to the Home Screen, before any screenshot or database check, and waits on SpringBoard for the "Rest is over" notification. It relaunches, checks the set reads done and the database holds 225 lb in kilograms, joins the two exercises in a superset, and checks the squat's warm-up starts no rest and a Romanian Deadlift set does. It kills and relaunches svett during that rest and checks the rest timer is back. It opens the plate calculator from the options for 225 lb, then `svett://tools/plates?kg=100` for the nearest loads, and finishes the workout. It presses only controls clear of the screen's bottom edge, so it never presses the keypad's Next and Done or the rest timer's buttons. Numbered screenshots go to `out-dir`, by default `~/svett-proof/<branch>/tools/`. It takes `SVETT_DEVICE_CMD`, `SVETT_METRO` and `--release` like `sim/tabs.sh`.

`sim/signin.sh` proves the account sign-in. It needs a build made with `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY` set to a Clerk development instance's publishable key, and fails with a message on a build without one. It stops svett, resets the simulator's Keychain, which drops any Clerk session, and puts `pnpm fixture --imported` in the database with no owner, after removing the account databases and the saved answer to the move offer. At the largest text size it shows the 300 imported workouts, opens Account through `svett://account`, shows both choices, and signs in with email as a new account. It moves the phone's data into it and checks the account shows all 300 workouts. Then it signs out, checks nothing is left without an owner, signs in as a second account, and checks it gets no second offer and shows none of the history. The accounts are Clerk test addresses (`+clerk_test`), whose code is always 424242, so no email is read. `SVETT_SIGNIN_EMAILS` overrides the two addresses. ### Server

`apps/server` is the phase 6 server, one Effect service on Node with PostgreSQL. Node runs its TypeScript directly, as it does the scripts. The root `Dockerfile` builds it. Coolify deploys that image as `svett-app` at `https://svett-app.jservers.net`, with the PostgreSQL database `svett-app-db`, whose address Coolify sets in `DATABASE_URL`. Run `jservers status`, `jservers logs` or `jservers deploys` from the repo to look at it.

`GET /health` answers `{"status":"ok","database":"ok","latestBackup":"<time>","restoreCheck":{...}}`. It answers 503 with `"database":"unreachable"` when the database does not answer. `restoreCheck` shows the newest backup the server restored to prove it works, when it did, whether it `restored`, and how many `tables` came back. It is `null` until the first check since the server started.

Accounts use Clerk. The server checks the Clerk session token in each request's `Authorization: Bearer` header against the instance's published keys, and takes the account from it. `GET /v1/me` names the signed-in account. Rows are keyed by account, table and ID, so two accounts that hold the same ID each keep their own, and any owner a request names is ignored. How phones push and pull rows, and which copy the server keeps, is in the next paragraph and in **Sync** under Effect and data patterns. The server reads `CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY`. The publishable key names the issuer and its key set. With `NODE_ENV=production` it turns sign-in off without both keys, with keys from different kinds of instances, or with an issuer on this machine, so it never trusts a stand-in. Outside production `CLERK_ISSUER` and `CLERK_JWKS_URL` may name a local issuer instead, as the tests' stand-in in `apps/server/src/test-issuer.ts` does. With sign-in off the server still starts and logs why. `/health` says `"signIn": "unconfigured"`, and every account route answers 503 with `sign_in_unavailable`. A token's `azp` must be one of the origins in `CLERK_AUTHORIZED_PARTIES`, separated by commas. Clerk leaves `azp` out of the iPhone app's tokens, which send no origin, so a token without one is accepted. A token must carry `aud` equal to `CLERK_AUDIENCE` when that is set, and may carry no `aud` when it is not. Clerk's free plan keeps a session 7 days.

The phone syncs through `PUT /v1/rows`, which takes up to 500 rows and answers which it `stored` and which are timed too far `ahead` of the server's clock, with the server's clock as `serverMillis`, and `GET /v1/rows?after=<seq>`, which answers the account's rows applied after that change number, a page at a time. Each request sends the `svett-sync-version` header with `SYNC_PROTOCOL_VERSION` from `packages/core/src/sync.ts`. The server answers 426 with `update_required` to a signed-in request without it or with an older one, before it reads or stores a row, and the phone says to update svett. Raise the version with any change the server needs from phones. Each applied change gets the account's next number while the account's row is locked, so numbers commit in order.

Profiles and follows live in the `profile` and `follow` tables. `GET /v1/profile` and `PUT /v1/profile` read and set the signed-in account's username and whether its profile is private. Usernames are unique whatever their case and follow `usernameProblem` in `packages/core/src/username.ts`. `GET /v1/profiles?prefix=<start>` searches usernames. `GET /v1/profiles/<username>` answers a profile with the first 50 activities the viewer may see, newest first by when each was shared, as the feed orders them, and a `next` cursor that `/activities?cursor=<next>` on the profile takes, under the feed's cursor rule, `PUT` and `DELETE` on its `/follow` follow and unfollow, and its `/followers` and `/following` list accounts 50 at a time, by username. A page's `next` is null on the last page, and otherwise `?after=<next>` asks for the page after it. `GET /v1/activities/<social id>` answers one activity the viewer may see, and 404 `not_found` for one they may not, as for one that does not exist. `GET /v1/follow-requests` lists the requests waiting for the signed-in account, each with its own `id`, and `PUT` or `DELETE` on `/v1/follow-requests/<id>` approves or declines that one request. An answer never looks up a username, because a username can pass to another account after the request was shown. A request already answered or taken back answers 404 `request_not_found`. A new profile is private, so each follower waits for approval. A public profile is followed at once, and making a profile public approves every waiting request. A follow and a change to the private choice both hold the profile's row lock, so no request made meanwhile is left waiting. You need a username before you can follow anyone.

Every read of another account's activities passes `privacy` in `packages/core/src/privacy.ts`, and `viewActivity` leaves out the hidden fields, so their values never leave the server for anyone but the owner. A block hides two accounts from each other, whoever blocked: profiles, search results, follower and following lists, feeds, posts, likes, comments and inbox items, and it refuses a follow, like or comment between them. Otherwise profile details, search and the follower and following lists are visible to every signed-in account. A private profile only means you approve each follower, so it still shows its `everyone` activities to strangers. Another account names an activity by its social ID, never its own ID, which for an imported workout is a UUIDv5 of its start time and would give a hidden start away. The server mints a random social ID in `activity_social` when a finished activity first arrives, and keeps it, so likes and comments can point at it. To prove it on the live server, with a Clerk development instance's secret key, run `CLERK_SECRET_KEY=sk_test_... node apps/server/src/social-proof.ts` from the repo. It signs in two Clerk test accounts, writes a followers-only, an everyone and an only-you activity as the first, checks the second sees only the everyone one as a stranger and while its request waits, and sees the followers-only one, without its hidden start time, once approved. It deletes what it wrote and ends the follow. `SVETT_SERVER` names another server.

The feed, likes, comments and the inbox live in `apps/server/src/feed-rows.ts`, and a post is named by its activity's social ID. `GET /v1/feed?cursor=<next>` answers the signed-in account's own posts and those of the accounts it follows, newest first by when each activity reached the feed, 20 at a time. That time is `shared_ms` in `activity_social`, which the server sets once when a finished activity first arrives, never from its start time, which may be hidden. Ties break by social ID. The cursor names the last post by its social ID alone, and the server takes it only while that post is still in the viewer's feed. Otherwise it answers 400 `invalid_cursor`, as for a cursor that names nothing. The feed and the inbox skip what the viewer may not see before they fill a page or count unread items. The feed needs a username, and answers 403 `username_required` without one. `GET /v1/posts/<social id>` answers a post with its comments. `PUT` and `DELETE` on its `/like` like and unlike, and both are safe to repeat. `POST` on its `/comments` with `{"body":"..."}` comments, up to 500 characters after `cleanComment` drops control and direction characters, and `DELETE` on `/comments/<id>` deletes one you wrote or one on your post. A post the viewer may not see answers 404 `post_not_found`, as one that does not exist does. `GET /v1/inbox?cursor=<next>` lists likes and comments on your posts, later comments on posts where you commented, follows and follow requests, newest first. Each item is unread when it is newer than the time `PUT /v1/inbox/read` with `{"until":<millis>}` last set. Every one of these reads goes through `privacy` and `viewActivity`, and a post's sets and route through `viewPostDetail` in `packages/core/src/feed.ts`, which leaves out hidden weights, heart rate and pace, every reading's time and the route's hidden ends. `WITHHELD` in `privacy.ts` names what hiding each field withholds, with every value that would give it back. A duration over a distance is a pace, so hiding pace withholds every duration too. A post reaches the feed about when its workout ends, so hiding the start time withholds every duration and the pace as well. A workout in progress never reaches a feed. Comments are someone's words, so the app shows them as plain text, and they never reach the coach. To prove the feed on the live server, run `CLERK_SECRET_KEY=sk_test_... node apps/server/src/feed-proof.ts`. Two Clerk test accounts find each other by username and follow each other, the first writes a lifting session and the second a run, each checks the other's post shows its own detail in its feed, and no hidden field reaches a feed, post or inbox answer. It undoes what it did unless `SVETT_PROOF_KEEP=1`.

Safety lives in `apps/server/src/safety.ts`, `social-rows.ts` and `account-deletion.ts`. `PUT /v1/profiles/<username>/block` blocks an account, ends any follow or request between the two either way, and `GET /v1/blocks` lists your blocks by ID for `DELETE /v1/blocks/<id>`, 50 at a time by username, paged with `?after=<next>` like the follower lists. `DELETE /v1/followers/<username>` removes a follower without blocking them. Each route runs through `Safety.asAccount`, which refuses a deleted account and takes a token from the account's bucket for its group: `likes`, `comments`, `follows`, `search` and `sync_push`, with the sizes in `RATE_LIMITS` in `packages/core/src/rate-limit.ts`. The buckets live in the `rate_limit` table, so they hold across a restart and across servers, and a refused request still spends its token. An empty bucket answers 429 `rate_limited` with `Retry-After` in seconds. `GET /v1/export` answers every row the server holds for the account, deleted ones too, as a svett file the app's import reads. `DELETE /v1/me` deletes an account in three steps. It records the deletion in the deletion ledger. Then it marks the account in `deleted_account` in a small transaction of its own, and from its commit every server refuses the account and every read leaves it out. Last it deletes every row that names the account in every table listed in `ACCOUNT_TABLES`, sets `rows_deleted`, and deletes the Clerk user through the Backend API with `CLERK_SECRET_KEY`, which ends every session. Outside production `CLERK_API_URL` names a stand-in Backend API. Without the secret key it deletes nothing and answers 502 `session_end_failed`, and when Clerk fails after the rows are gone, the server keeps trying, and sending it again finishes too. From then on any request carrying the ID, such as an upload from a phone that was offline, answers 410 `account_deleted` and writes nothing. A deletion takes the account's advisory lock alone, and every request holds it shared, so nothing a request writes outlives the deletion. A write that names another account, a block, follow, follow approval, like or comment, also holds that account's lock through `lockOther` and checks the account still exists, so another account's deletion either deletes what the write wrote or refuses it as not found. A request waits for account locks only in ascending order of account ID, and only tries one below a lock it holds, so two writes never wait for each other. Block, unblock, follow, follow request, approval and remove-follower also take the lock of the two accounts' pair alone through `lockPair`, after every account lock and before any row lock, and a follow or approval checks for a block only once it holds it. So a follow or request either commits first and the block removes it, or waits for the block and is refused, and none survives a block either way. Every like, comment, follower, following and request count leaves out each account in a block with the viewer, so a count matches the list the viewer can open and never shows hidden activity. A new table needs its account columns in `ACCOUNT_TABLES`, or a reason in `KEPT_TABLES`, or the deletion test fails. Every read that shows another account's profile, follows, posts, likes, comments, inbox items or search results leaves out an account with a `deleted_account` row, through `hiddenFrom` in `social-rows.ts`, the same filter that leaves out a block, and `hiddenBetween`, which the privacy rule takes as `blocked`. The deletion ledger is the directory `deleted-accounts/` in `BACKUP_DIR`, and each deletion is synced to disk there before the database hears of it. Its `ledger.json` holds `{"ledger":"<random ID>"}`, written once. It is written to a temporary file, synced, and linked into place only when no `ledger.json` exists, so two servers making a ledger at once end with one. The database keeps the ledger's ID in `deletion_ledger`. Each deletion is its own file, `<account ID>.<receipt hash or none>.json`, holding `{"account":"<ID>","at":<ms>,"receipt":"<hash>"|null}`. A deletion writes its file under a temporary name starting with `.tmp-` until the whole entry is stored, fails when a write stores nothing and removes the temporary file, syncs it, renames it to its final name and syncs the directory. Two deletions never write the same file, so the ledger needs no lock, and a crash leaves at most a temporary file. A read lists the directory and reads every file under a final name, never a temporary one. Once an entry is renamed into place the deletion is accepted, and the account counts as deleted for every purpose. Each server keeps the ledger's accounts and receipt hashes in memory, read on every start and added to by each entry it writes. Before each account check and each receipt lookup it reads the directory's modification time, and when that changed, or changed less than a second before the last read, it reads the files it has not read yet. So a server also learns of an entry another server wrote, even one that died before marking the account. `Safety.asAccount`, `lockOther` and `GET /v1/deletions/<receipt>` check the ledger, beside `deleted_account` and `deletion_receipt`. So when the directory's sync, the mark or the process fails after the rename, every request of the account answers 410 `account_deleted` and writes nothing, and `GET /v1/deletions/<receipt>` answers `{"deleted":true}`, on every server that reads the ledger. The server then finishes the deletion itself, from the first step not done. It marks the account with every receipt the ledger holds for it, deletes every row of the account unless `rows_deleted` says they are gone, deletes the Clerk user, which counts a user already gone as deleted, and sets `sessions_ended`. Running it twice changes nothing. It runs at once after any failed step, and when that fails it keeps trying in the background, after 1 second and then twice as long each time, up to 5 minutes. A server that finds another server's entry finishes that deletion the same way. The mark and the row deletion each take the account's lock alone, so a sync push or a like, comment, follow or block in flight commits before the mark, and the row deletion deletes what it wrote, or it waits and then sees the mark and is refused. Each start, after a restore too, deletes again every account in the ledger that the database does not mark with `rows_deleted` before it serves, then calls Clerk for every deleted account whose `sessions_ended` is false, and leaves one that fails to the background. A `DELETE /v1/me` sent again finishes it the same way. Each start removes temporary files more than a day old, which are deletions that were never accepted, and logs how many. The ledger outlives a restore, which the database's own `deleted_account` does not, and the server applies it again after `cli.ts restore` and on every start before it answers a request. Backups keep a deleted account's rows for up to 14 days, until they age out after `BACKUP_KEEP` backups, and a restore from one deletes them again. `DELETE /v1/me` takes an optional body `{"receipt":"<secret>"}`, of 43 to 100 letters, digits, `_` or `-`. The server keeps only its hash, and `GET /v1/deletions/<receipt>` answers `{"deleted":true}` once a deletion with it happened. It needs no session, as the deletion ended them all. It refuses a receipt that is not well formed with 400 before it reads the ledger or the database. On the phone, Delete account on the Account screen asks whether to keep a copy on the phone or erase it, then asks once more. The move journal saves the deletion, the choice and a new receipt as `deleting` before the request is sent. Every launch finishes a saved deletion: it sends it again, and when the answer does not settle it, asks with the receipt. Once the server deleted the account, keeping copies the account's rows into the phone's own database through the journal's `keeping` and `erasing` states, then deletes the account's file, so a crash finishes the same choice at the next launch. The journal goes back to what it was only when the server refused and says it deleted nothing. To prove it on the live server, run `CLERK_SECRET_KEY=sk_test_... node apps/server/src/safety-proof.ts`. A second test account follows the first, the first blocks it, and the proof checks the blocked one finds no profile, search result, feed post or post and cannot follow, like or comment, then unblocks. A third test account writes a row, exports it, keeps a session token as an offline phone would, and deletes itself. The proof checks Clerk gives it no new token and the old token's upload answers `account_deleted`.

Server migrations go at the end of `MIGRATIONS` in `apps/server/src/migrations.ts`, keyed `<id>_<name>`. They run when the server starts. Never edit one that has shipped.

The server backs up its database with `pg_dump` into `BACKUP_DIR`, which is `/backups`, a Coolify volume that outlives each deploy. It takes one on start when the newest is more than a day old, then one every night at 03:00 UTC (`BACKUP_CRON`). It keeps the newest 14 (`BACKUP_KEEP`). A dump gets its `svett-<time>.dump` name only once it is complete, and never replaces a backup that has the name. One backup of a database runs at a time, across every server and the command line, through a PostgreSQL advisory lock. Another one skips and logs why. After each backup, and for the newest one on start, the server restores it into a new, empty scratch database `svett_restore_<tag>_<time>_<random>` on the same PostgreSQL, where `<tag>` stands for the live database, counts the tables, and drops it. Each check has its own, so checks on several servers never meet. A check holds an advisory lock named for its scratch database until it drops it, and gives up and drops it after 6 hours. On start the server drops its own live database's scratch databases more than a day old, which a crash left behind. Advisory locks only reach sessions on the same database, so it never touches another live database's. It takes each one's lock first and skips any that a running check still holds. To take one now, run `node apps/server/src/cli.ts backup` in the container. It fails if another backup is running.

To restore, create an empty database on the same PostgreSQL and run this in the server container:

```sh
RESTORE_DATABASE_URL='<the empty database>' node apps/server/src/cli.ts restore /backups/<file>
```

It refuses a database that already holds a table, so it never merges into live data. It then migrates the restored database and deletes again every account in the deletion ledger, the directory `/backups/deleted-accounts/`, and logs how many. Then point `DATABASE_URL` at the restored database with `jservers env set` and restart. The server applies the ledger again on start, and ends the Clerk sessions of each account it deleted again, so a database restored some other way loses its deleted accounts before it serves. Never delete or edit the ledger's files.

A start and a restore both check the ledger first. A database that names no ledger, a new one or one from before the ledger had an ID, takes the ledger in `BACKUP_DIR`, records its ID, and deletes again every account in it. When there is no `ledger.json`, the server makes one only for a database that holds no account rows in any table of `ACCOUNT_TABLES`, as no deleted account can then come back. A database that holds accounts and names no ledger refuses to start or restore without it, and the message says how many accounts it holds. First look for the ledger on the volume as below. Only when the ledger is lost for good and every account in that database should exist, start or restore once with `NEW_DELETION_LEDGER=true`. The server then makes a new ledger, logs a warning that names the number of accounts it now keeps, and asks you to unset the variable. Never set it by default, since any account deleted after the database's backup comes back with it. A database that names a ledger refuses to start or restore when `ledger.json` is missing or holds another ID, and the message names both. Then check that `BACKUP_DIR` is `/backups` and that the Coolify volume is mounted there, and never let the server make a new ledger in its place. A file under a final name that does not parse, or whose name does not match its entry, also refuses and names the file, since the server can no longer tell which accounts were deleted. So do deletion files without a `ledger.json`. Mend that file from a copy of the volume before you start again, and never touch the temporary files. A backup holds a deleted account's rows until it ages out, at most 14 days.

The first deploy of the deletion ledger meets this refusal when the live database already holds accounts, such as the test accounts of `signin.sh`, `social-proof.ts`, `feed-proof.ts` or `safety-proof.ts` run against the live server, since no account was deleted before the ledger existed. Then deploy once with `NEW_DELETION_LEDGER=true` set through `jservers env set`, and check that `jservers logs` says `NEW_DELETION_LEDGER is set, so made a new deletion ledger` with the number of accounts. Then unset it and restart, and check the next start logs no such line.

The server tests start PostgreSQL in Docker and run `pg_dump` and `pg_restore` from the same image, so Docker must be running. Both images are `postgres:16-alpine`, the deployed database's version, unless `SVETT_TEST_POSTGRES_IMAGE` or `SVETT_TEST_PG_TOOLS_IMAGE` says otherwise. The Dockerfile installs the client tools of that same major version, because a newer `pg_restore` sends settings an older server refuses. Change the three together.

### Simulator scripts inside T3 Code

An agent in T3 Code must drive the simulator through the command that T3's `device_open` tool returns, never through `simctl launch`, `simctl openurl` or its own `agent-device` session. The scripts follow that rule when `SVETT_DEVICE_CMD` holds the command. They still build with `xcodebuild` and install with `simctl install`. Without the variable they behave as before, for use outside T3.

1. Call `device_list` for rena-devbook and find `svett iPhone 16 Pro Max` on iOS 27. If it is missing, create it with `xcrun simctl create "svett iPhone 16 Pro Max" "iPhone 16 Pro Max" <iOS 27 runtime>` and list again. To use another iOS 27 simulator instead, set `SVETT_SIMULATOR` to its exact name. The scripts install on that simulator, so it must be the one you open.
2. Call `device_open` with its `hostId` and `id`.
3. Run the scripts with the returned command in `SVETT_DEVICE_CMD`, in the same shell command, because environment variables do not carry over between an agent's shell calls:

   ```sh
   export SVETT_DEVICE_CMD='<the command device_open returned>'
   ~/svett-app/scripts/devbook-build.sh <branch> && ~/svett-app/scripts/sim/tabs.sh
   ```

   `sim/launch.sh` takes the same variable, so `~/svett-app/scripts/sim/launch.sh -svettFixture <path>` relaunches with a fixture.

4. Call `device_close` when done. With `SVETT_DEVICE_CMD` set, `tabs.sh` does not close the session itself.

## Effect and data patterns

The data layer lives in `packages/core`. Follow these patterns so every table stays ready for export, import and sync.

**Schemas.** Every table has one Effect Schema in `packages/core/src/schema.ts`. Its keys are camelCase, and each key's SQL column is the snake_case form. Spread `rowFields(SomeId)` into it, so the row has `id`, `updatedAt` and `deletedAt`. Give each table its own branded ID (`ActivityId`, `ExerciseId`). Write enums as `Schema.Literals`. Put a rule that spans fields in `.check(Schema.makeFilter(...))`, as `ActivitySet` does for "a set records reps, a time or a distance". Rows are checked against the schema on every write and parsed on every read.

**Tables and migrations.** A new table needs its schema, an entry in `TABLES` in `packages/core/src/table.ts`, and a new migration at the end of `MIGRATIONS` in `packages/core/src/migrations.ts`. Never edit a released migration. Never add SQL `CHECK` constraints for enums, or foreign keys. SQLite can only remove them by rebuilding the table, and sync may deliver a child before its parent. The migration test fails until the table's columns match its schema.

**Repositories.** Only a repository writes its tables. Screens and features never run SQL. Each repository is a `Context.Service` in `packages/core/src/repositories/` with a `layer` built by `Layer.effect`. It captures `Sql` and `Ids` and returns plain methods built from `insertRows`, `selectRows`, `updateRow` and `softDeleteRows` in `table.ts`. Wrap a write that touches several rows in `sql.transaction`. Deletes are soft. Deleting a parent deletes its children with the same `deleted_at`, and a restore brings back exactly the rows with that time. Reads never return deleted rows.

**Export and import.** `TransferRepository` writes a svett file's whole rows with their own IDs, and puts back what an import replaced. Phase 6 sync will apply rows the same way. Besides it, only `copyDatabase` in `packages/core/src/database-move.ts` writes every table, when the phone's data moves into an account. A new table also needs its parent in `PARENT` in `packages/core/src/transfer.ts`, or the type check fails, and the round-trip test in `repositories/transfer.test.ts` fails until it puts a row in the table. A file's version is `SVETT_FILE_VERSION`. Raise it with any change to the file's shape. A file holds every row, deleted ones too, so a deletion survives the round trip. An import only adds or replaces the rows the file holds. It never removes a row the file leaves out. Every import records each record it added or replaced in `import_change`, with the IDs of the rows it wrote and the versions they replaced, and Undo works from those rows. Library exercises share the time `LIBRARY_UPDATED_AT` until edited, so every install holds the same library rows.

**Workouts in progress.** One workout at most is in progress. `ActivityRepository` refuses a start, a restore or an update that would make a second one, with `WorkoutInProgressError`. A workout in progress is not history yet. Every query for history, the calendar, streaks, charts, records, muscle volume, counts or export reads only activities with `status = 'finished'` and sets with `done = 1`. A workout in progress is a draft on the phone that started it, so it is never exported, imported or synced. `withoutDrafts` leaves it and every row below it out of an export. An import skips a record whose workout is in progress in the file or here, and its preview counts it as skipped. Undo never puts a workout back in progress beside another one. It keeps that workout discarded and counts it in `discarded`. A field added to a table after svett files existed goes in `addedFields` in `packages/core/src/transfer.ts` with the value its migration gave older rows, so older files and import journals still read and their fingerprints stay the same. A value the migration worked out from other rows comes from the same rows there, as an exercise's set fields come from its sets.

**Logging a workout.** The rules are pure functions in `packages/core/src/logger.ts`: what an exercise's sets record (`setFields`), last time's set for each set (`matchPrevious`), marking a set done (`markDone`), and what finishing keeps (`finishPlan`). `start-workout.ts` composes them with the repositories. The app's logger in `apps/mobile/src/workout/` saves every change through `ActivityRepository` as it is made, through one queue in `store.ts`, so a killed app reopens the workout as it was. A set edit shows at once and saves behind. Nothing about a workout lives only in React state.

**Hevy import.** Another app's file goes through the same `planImport`, `applyImport` and Undo as a svett file, as an `ImportInput` whose `read` builds its rows from the rows here. `hevyImport` in `packages/core/src/hevy-import.ts` does that for Hevy's workout CSV, which `decodeHevyFile` reads. A Hevy workout's identity is its start time as the file writes it, which has no time zone. A workout whose Hevy content has the same `fingerprint` as when it was imported comes back as it is here, so edits made in svett never show as changes. Hevy's exercise names map to the library through `HEVY_LIBRARY` in `hevy-exercises.ts`. The match screen asks for the rest, and `exercise_alias` remembers each choice. A name kept as new becomes a custom exercise with the ID `hevyExerciseId(name)`. Each imported exercise records what its sets hold, as `setFieldsFromSets` decides, so the logger starts it that way next time.

**IDs and time.** A new row's ID comes from its `Origin`. Rows made in svett get a UUIDv7 from the `Ids` service. Imported rows get a UUIDv5 of their source and source identity through `importedId`, and their children add a path such as `/exercise/0/set/2`. Library exercises use `libraryExerciseId`. Read time from Effect's `Clock`, never `Date.now()`, and never use `Math.random()` for IDs.

**Routes.** A recorded route is one line per stretch between pauses, kept in each location sample's `segment`. Distance, splits, climb, the map and the elevation chart never join two stretches. Anyone but the owner, such as the feed or an export for someone else, reads a track only through `sharedTrack` in `packages/core/src/cardio.ts`, which leaves out the hidden start and end. The hidden start ends where the route first leaves a circle of `hideStartM` around the first reading, and the hidden end begins where it last enters one of `hideEndM` around the last. Only the owner's own screens read the samples.

**GPS readings.** Every reading passes through the filter in `packages/core/src/track-filter.ts` before it counts. It is a constant-velocity Kalman filter with noise from each reading's accuracy and process noise per sport in `MOTION`. It drops readings outside its Mahalanobis gate and counts a reading once a later one confirms it. Each confirmed reading is marked moving or paused once, when it arrives, and never again. A reading that reports a speed says still below 0.3 m/s (`STILL_SPEED_MPS`) and moving at 0.4 m/s or more (`MOVING_SPEED_MPS`). Four readings in a row saying still pause the recording (`PAUSE_READINGS`), and three saying moving resume it (`MOVE_READINGS`). A reading with no speed decides from positions instead. A paused recording moves once a reading lies outside the gate around where it stopped, and a moving one stops when the filter got no further in 20 seconds than 0.3 m/s would take it. Distance is the path through the first reading and every moving one, so a pause adds nothing, and each step is capped by how far the reported speeds say you went. Positions are smoothed with a Rauch-Tung-Striebel pass and settle once `LAG` readings follow them, so what the recording shows is what it saves. Each stretch between pauses gets its own filter. Without speeds, drift where a recording stopped looks like movement as each reading arrives, so the filter also looks back at the readings with no speed that have stayed within `DRIFT_RADIUS_M` of their centre for `DRIFT_MS` and turned sharply as often as drift does (`DRIFT_REVERSALS`). Those not yet settled are paused after all, and the path ends where they began. Routes imported from Apple Health and GPX run through the same filter in `packages/core/src/imported-route.ts`, one filter per track segment. A Health workout keeps the distance Health measured, and its splits are scaled to add up to it.

**Databases.** `databaseLayer(driver, ids)` migrates, seeds the exercise library and provides every repository. Each owner has its own file, named by `databaseFileName`. The app opens it with expo-sqlite in `apps/mobile/src/data/database.ts`.

**Tests.** Tests run on `node:sqlite` in memory. `openTestDatabase()` in `packages/core/src/test-database.ts` returns a migrated, seeded database with a manual clock and seeded IDs. Test through the repositories and assert what a caller sees. Read the SQLite file directly only to check what a repository cannot show, such as deleted rows.

**Weights.** svett stores kilograms. Pounds are a way to show and type weights, set on the You tab's Units and plates screen, and `weight-unit.ts` is the one place that converts and rounds. A weight field that still reads as the stored weight keeps it exactly, so 225 lb saved again does not drift. Units and RPE live in the phone's user defaults through `apps/mobile/src/settings/store.ts`, because they change how weights show, not what is stored. Your plates and bars are data you made, so they are rows of the `gear` table, one per unit, written by `GearRepository`, and they travel with export and import. A running rest is kept in user defaults by `apps/mobile/src/workout/rest.ts`, so it outlives a killed svett, and is never exported.

**Sync.** Every write to a synced table queues its row in `sync_outbox`, through SQLite triggers, so no repository has to remember to. Writes sync applies, and the bundled library's seeding, run with `sync_state.quiet` set and queue nothing. `syncOnce` in `repositories/sync.ts` sends the queue and then saves what the server applied since the cursor, a page and its cursor in one transaction. `mergeRow` in `sync.ts` is the one merge rule, on the phone and the server: the later `updatedAt` wins, and on equal times the higher change ID, a hash of the row. A delete is a row with `deletedAt` set. Row times come from `currentTime`, a hybrid logical clock kept in `sync_state.clock`: each write takes the later of the wall clock and one past the last time, and each applied change raises it, so writes stay in order across equal milliseconds, a clock moved back and a restart. Coach chats and proposals never sync, nor does an import journal that names or keeps one at any depth (`staysOnPhone`), and the server refuses such a row. Neither does a workout in progress or any row under it. The queue triggers skip those rows, finishing the workout queues every row it has, deleted ones and ones written while in progress too, each with its own time, and putting it back in progress takes them out of the queue. A pull never changes a workout in progress here or any row under it, whatever the queue holds and in whatever order its rows arrive. It keeps the pulled copies aside in `sync_aside`, a table that never syncs, through `keepAside` in `repositories/sync-rows.ts`. Putting a finished workout back in progress also keeps aside its rows as they were then. When the workout is finished, `settleKeptAside` merges each copy with the row here by `mergeChange`. A row this phone lacks, such as a set another phone added, is added. The later change to a row wins. A delete of the workout, or of an exercise, drops every later edit under it, this phone's own too. A row this phone changed there after the delete goes back to the other phones' copy, and a row only this phone has, such as a set it added, is removed. The workout row merges with its version from before Finish, since finishing ends the draft and is not an edit that beats another phone's. So a workout another phone deleted while it was in progress here is deleted here too once it is finished, and Undo brings it back as it was. Discarding a workout in progress sends nothing written while it was in progress. A workout other phones have goes back to the copies kept aside, as it was before it was put back in progress plus every change other phones made since, and those copies are queued again. So a discard here never deletes or changes a row another phone wrote. A field added later to a workout table must also be filled in the rows of `sync_aside`, as in import journals. The server refuses a workout in progress, and every row a push puts under one. A table added later needs its queue triggers in its own migration. `mergeChange` adds deletes to the rule: a live copy of a row under a deleted workout, changed at or after that delete, loses to the deleted copy, so Undo brings back what the workout had. The server, where every phone's changes meet, goes further with `mergePushed`. A change to a workout row timed at or after a deletion of that row or of a row above it, and before an Undo of that deletion, was made by a phone that had not seen the delete, and is dropped, whatever it is. Only an Undo of that very deletion brings the row back. The server keeps each Undo it took of a row in `account_row.restored`, so a delete that arrives after a later change still beats it, unless the server took an Undo of that delete, and the outcome is the same in either order. Of two deletes, the earlier one stays. A workout row timed before a deletion above it is kept deleted with that deletion, and when the server takes a delete of a workout row it also deletes each live row under it that the push did not, as the phone's delete would have. One changed before the delete goes with it, so Undo brings it back, and one changed at or after it is a dropped change and stays deleted. A write here that brings back a deleted workout row, such as Undo or an import, records the deletion it reverses in `sync_restore`, a table that never syncs, through triggers, but only when the server may hold that deletion. Each deletion written here waits in `sync_unsent_deletion` until `SyncRepository.sending` records that a push carrying it is leaving, and an Undo of a deletion still waiting there drops it without naming it, since it never left the phone. So offline delete and Undo cycles add nothing, and `sync_restore` holds only deletions that were sent or pulled and are not settled yet. The push sends every deletion recorded for the row as its `restores` list, and the server takes the change when the list holds the deletion it has. A confirmation drops only the deletions that push sent, so an Undo made while a push is on the way names both the deletion before it and the one it carried, whether that push arrived or not. A list longer than one push takes goes out across several pushes, newest deletions first, through `pushesOf`, and the row is confirmed after the last. The server refuses any other such change. It gives the copy it keeps a new change number, or keeps a dropped new row as a deleted copy at the row's own time, and confirms the change, so the phone stops sending it. The phone takes the server's copy of any row it has no unsent change to, so every phone ends with the server's rows. When the server held changes as too far ahead and the phone's clock is right again, `syncOnce` moves them to new times after every other change here, keeping their order and each delete's shared time, and sends them again.

**Privacy.** One pure function, `privacy` in `packages/core/src/privacy.ts`, decides what one account sees of another's activities from the viewer, the owner, the follow state, a block and the activity's audience and hidden fields. Its test table lists every combination. The server reads `blocked` from the `block` table, either way round. Add any new field that can be hidden to `HiddenField` and to `viewActivity`, or to the view of the rows that carry it.

**Progress.** Records, chart series, weekly sets per muscle and measurement summaries are pure functions over `PerformedSet` rows, in `records.ts`, `exercise-progress.ts`, `muscle-volume.ts` and `body-measurements.ts`. `ProgressRepository` reads those rows in workout order and writes nothing. Each number comes with the rule the app shows beside it, such as `RECORDS_RULE` and `MUSCLE_SET_RULE`. Change the rule text when the counting changes.

**Fixture.** `pnpm fixture` writes `.fixtures/svett-fixture.db` with 300 strength workouts, about 6,000 sets over two years, three routines and body measurements. The same seed always gives the same rows. To prove it in the simulator, run `scripts/sim/fixture.sh` on rena-devbook after `devbook-build.sh`, with the same `--release` choice and `SVETT_DEVICE_CMD` as `tabs.sh`:

```sh
~/svett-app/scripts/sim/fixture.sh [--release] <out-dir>
```

It generates the fixture into `<out-dir>`, copies it into the app's data container, and screenshots the Progress tab's counts twice. `01-anonymous.png` is a plain launch. `02-fixture.png` is a relaunch through `launch.sh` with `-svettFixture <absolute path>`.

`scripts/sim/hevy.sh` proves the Hevy import with the synthetic samples in `packages/core/test-data`, which follow Hevy's column layout. On a new empty database it imports the sample through `svett://import?file=<name>&kind=hevy`, matches one unknown name, presses Done, opens the sample again and expects nothing new, takes the changed sample's changed and renamed workouts, and undoes that import, checking the database after each step. `summary.txt` and the screenshots go to `<out-dir>`, by default `~/svett-proof/<branch>/hevy/`.

`scripts/sim/data.sh` proves export and import on the fixture. It exports through the share sheet, launches on a new empty database file, imports the export through `svett://import?file=<name>`, and checks the result equals the fixture row for row, deleted rows included, with `scripts/compare-databases.ts`. It imports the same file again and expects nothing new, then undoes the import from Your data. The export, both comparisons, `summary.txt` and the screenshots go to `<out-dir>`, by default `~/svett-proof/<branch>/data/`.

`scripts/sim/health.sh` proves Apple Health and GPX import. `scripts/health-proof.ts` writes a made-up `export.zip` and GPX ride into svett's Documents and a database holding one Hevy-shaped strength workout. The script opens svett on that database, previews the export through `svett://health-import?file=<name>`, checks the line atop the preview, and declines. The export holds one run whose dates are not dates, on purpose, so the preview says svett could not read 1 of its entries, and `proof.txt` says so. Then it imports the export, which links the Health copy of the Hevy workout and gives it the Health heart rate. It imports the export again and expects nothing new, imports the GPX ride, opens the linked workout through `svett://activity/<id>`, and saves a ride through `svett://manual`, whose query fills the form. At the largest text size each screen's buttons sit below it, and agent-device's `wait` sees only what is on screen, so the script waits for an element at the top of each screen, then scrolls each button on screen and drags it clear of the bottom edge before it presses its centre. After each step `scripts/health-proof.ts check` reads the database and the script fails on any check that does not pass. Screenshots and `proof.txt` go to `<out-dir>`, by default `~/svett-proof/<branch>/health/`.

**Apple Health.** A free Apple account cannot sign the HealthKit entitlement through AltStore, so svett reads Apple Health's export file instead of HealthKit. `packages/core` streams `export.xml` out of `export.zip` a megabyte at a time, so a real export of hundreds of megabytes never sits in memory whole. export.xml has no stable workout ID, so a Health workout's identity is its start time, type and source. A GPX file's identity is its first point's time. A workout that overlaps one from another source is a possible duplicate, and linking it records the second identity in `activity_source`. Never commit a real Health export.

`pnpm fixture --imported` brings the same workouts in as one Hevy import instead, as `sim/signin.sh` uses it.

**Accounts on the phone.** Each owner has its own database file, so one account never reads another's rows. `apps/mobile/src/data/current.ts` holds the open one. A new Clerk session opens its account's database. A session that lapses after 7 days keeps the account's database open, logging goes on into it, and the Account screen says to sign in again to sync. Only Sign out opens the database with no owner. Every screen reads through `appDatabase()` and writes through `write` in `data/store.ts`, and reads again after a switch. A write made for one database refuses once another is open, and so does Undo of a deleted workout, whose offer closes when the account changes. It remembers the last owner and opens that database at launch, so an offline launch still opens the account's data. The first sign-in offers once to move the database with no owner into the account. Moving copies every row with its ID through `copyDatabase` and then deletes the file with no owner. Starting empty leaves it on the phone, and it opens again after sign out. The answer is a journal kept outside every database, through `startMove` and `finishMove` in `packages/core/src/move-journal.ts`. It names the account before the copy starts. Until the file with no owner is deleted, signing out opens an empty database instead of it, which refuses every write, the Account screen says the move is unfinished, and no other account is offered the move. Each launch and each sign-in finishes a move a crash cut short, into the account the journal names. Both sign-in choices are steps of `signInStep` in `packages/core/src/sign-in.ts`. The Account screen opens from the You tab or `svett://account`. A build without `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY` has no accounts and says so there.

iOS turns `-key value` launch arguments into user defaults, which React Native's `Settings` module reads, so the switch needs no native code. Without it the app opens the anonymous database. The Progress tab shows the counts it read.

## Coach

The coach sends `POST https://api.openai.com/v1/responses` from Swift, in `CoachClient` in `ChatGPTCore`, with the ChatGPT sign-in's token. JavaScript builds each request body and gets back only `CoachEvent`s: text deltas, tool calls, and `done` or `failed`. No token reaches JavaScript.

`askCoach` in `packages/tools` runs one question: it builds the request, checks it with `checkResponsesRequest` against OpenAI's plan usage rules, runs the tool calls and keeps every turn in `coach_message`. It never resends a failed request. Read tools are in `packages/tools/src/tools.ts`, each with an Effect Schema input and output, a bounded answer and a `source` that the answer shows under "Read:". Add a tool there, and it goes to the model in the `svett` namespace. `COACH_METHOD` switches between tool calls, which ship, and the plan's summary fallback.

The tests replay `packages/tools/fixtures/*.json` on the generated database and check every request against the recording. A live run with `scripts/sim/coach.sh --live` records a new one.

**Proposals.** The coach is read-only except for `propose_routine` and `propose_program`, in `PROPOSAL_TOOLS`. They only store a pending row in `proposal`, linked to the user's question, with the plan in its payload. Every exercise must exist, and a refusal goes back to the model and shows in the chat. `applyProposal` and `undoProposal` in `packages/core/src/proposals.ts` write through `RoutineRepository` in one transaction. Apply records the routines and folder it created with a fingerprint of them and every row below them. Undo deletes exactly those, and refuses when the fingerprint changed, because the user edited, moved or deleted something since. Applying twice creates nothing the second time. No tool edits or deletes an existing routine.

## Design system

Screens build on the components in `apps/mobile/src/ui` and the tokens in `apps/mobile/src/design`. The design gallery on the You tab shows each one in its states.

**Colours.** svett is dark only, whatever the phone's appearance setting, so `app.config.ts` sets `userInterfaceStyle: "dark"`. `apps/mobile/global.css` defines every colour token once. Use them as classes, such as `bg-surface` or `text-secondary-label`. Props that take a colour instead of a class, such as an SF Symbol's tint or an SVG stroke, get the current value from `useColor(token)`. A new token goes in `global.css` and in `COLOR_TOKENS` in `tokens.ts`. `tokens.test.ts` fails until both lists match and every pairing the components use passes WCAG AA contrast. Set types and sports map to their colours through `SET_TYPE_COLOR` and `SPORTS`.

**Text.** Use `AppText` with a `variant` named after an iOS text style, such as `body` or `headline`, and a `tone` for its colour. Each variant passes its own `dynamicTypeRamp`, so text scales with Dynamic Type on Apple's curve. Do not cap text size, except on keypad and stepper digits.

**Large titles.** A screen under a large title, which every tab has, must start with its scroll view or list, with `contentInsetAdjustmentBehavior="automatic"`. A large title makes the header translucent, so the content starts under the bar and a plain `View` draws under the title. The title collapses, and what scrolls under the bar blurs, only for the scroll view UIKit tracks, and UIKit does not track a list inside a wrapping `View`. Put overlays such as an undo bar after the list. `large-titles.test.tsx` checks every large-title screen.

**Large text.** Nothing may clip at the largest accessibility text size. `useIsAccessibilityTextSize()` is true at the five accessibility sizes, and layouts that put things side by side stack them there, as `ListRow` and `SetRow` do. Native segments do not grow with text, so `SegmentedControl` shows its options as rows there. Run `scripts/sim/gallery.sh` to check.

**Controls.** Every control has an accessibility role and label, and a target of at least 44 points (`min-h-target`). Controls used mid-set, such as the keypad and stepper, use the larger `key` size. Native controls come from `@expo/ui` where one fits, such as the segmented control and the sheet. `src/accessibility.test.tsx` draws every screen in `App.tsx` on a fresh install, with data, and at the largest text size with a workout in progress, and fails on a pressable without a role, a label or a 44 point target, a switch or field without a label, a symbol neither labelled nor hidden, or a chart or map without a text summary. A screen test can run the same check on what it drew with `unlabelledControls` from `src/test-accessibility.ts`, as the social and feed tests do.

**Empty states.** A screen that can be empty shows `EmptyState`: what goes there, and the one action that fills it, such as Import workouts on an empty history.

**Runtime.** The app runs on the Hermes that React Native 0.88.1 pins, which lacks some newer JavaScript, such as `Array.prototype.toSorted`, `Temporal`, `Uint8Array`'s base64 methods and every `Intl` formatter but `Collator`, `DateTimeFormat` and `NumberFormat`. Tests run on Node, which has them, so code can pass every test and still throw on the phone. Lint refuses the missing APIs in app code; the list and how to recheck it after a Hermes bump are in `vite.config.ts`.

**Logic.** Components show values and report presses. Formatting and input rules live in `packages/core` with tests, such as `setBadge`, `editNumberEntry` and `niceTicks`.
