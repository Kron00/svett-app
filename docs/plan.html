svett build plan

Draft for your approval. Written 13 November 2026. Nothing is built yet. Building starts when you say go.

The short version. svett is one iPhone app for lifting and cardio. It has one feed for every kind of workout. You can take all your data out and bring it back in. A coach inside the app runs on your own ChatGPT plan after you tap Continue with ChatGPT, so nobody pays svett for AI.

This plan builds the app in 8 phases and 26 pull requests. Each pull request is built, run in the iPhone 16 Pro Max simulator, reviewed by GPT Sol in a loop, and then scored by a council of Claude Opus and GPT Sol. A pull request merges only when both score it 9 or higher. Every merge ships a new version to your phone through AltStore.

6. How it is built

The data shape comes first

Everything you do is an activity. A lifting session, a run, a manual entry and an imported workout are all activities. The details hang off the activity. That one decision is what makes one history, one feed and one export possible.

TableHolds
activityKind (strength, run, ride, walk, hike, other), start, duration, title, notes, where it came from (logged here, imported, Apple Health), who can see it, which fields are hidden.
activity_exercise, activity_setFor strength. The exercises in order, the superset group, and each set with its type, weight, reps, time, distance and RPE.
activity_track, activity_sampleFor cardio. The GPS route, splits, elevation and heart rate.
exerciseThe library and your custom exercises, with primary and secondary muscles and equipment.
routine, routine_exercise, routine_set, folderSaved plans.
measurementBody weight and tape measurements. Always private in version 1.
import_batchOne row per import. Every imported row records its batch, its source, its identity in that source, and a fingerprint of its content.
coach_messageThe coach chats, kept on the phone only.
proposalA change the coach or a connected assistant wants to make, with its preview and whether you applied it.

Rules the code keeps

  1. The phone works alone. Logging, history, progress, export and import work with no network and no account. The coach is the exception in phases 0 to 5. It needs a ChatGPT sign-in and a connection.
  2. Every row is ready for sync from the first schema, in F4. Each row has a unique ID, a time it changed, and a deleted marker. A row you create gets a random ID. A row imported from Hevy or Apple Health gets an ID computed from its source and its identity there, so two devices that import the same workout make the same row. The server keys every row by account and ID together, so two people who import workouts with the same start time each keep their own. Adding the server in phase 6 changes no IDs and rewrites no tables.
  3. One writer per kind of data. Screens never run SQL. A repository per table group does, and it is the only code that writes those tables.
  4. Outside data is parsed at the edge. Import files, model answers and server responses pass through an Effect Schema. Code past that point trusts its types.
  5. An assistant proposes and you apply. No assistant, inside the app or outside it, changes data without a tap from you. Every applied proposal can be undone.
  6. ChatGPT plan tokens stay on the phone. The svett server never receives them and never calls a model.
  7. One function decides who sees what. Every server read goes through it. Tests list every combination of audience, follow state and hidden field.
  8. One account's data never mixes with another's. Each account has its own database file and its own queue of unsent changes on the phone. The server sets the owner of every row from the signed-in session and ignores any owner the phone sends.

Continue with ChatGPT

The flow is OpenAI's documented one for open-source apps. Your interval tracker already runs it, and you signed in with it on your iPhone on 13 November. svett ports that code into a Swift module inside the Expo app.

  1. You tap Continue with ChatGPT. The app starts a small listener on 127.0.0.1, on a port iOS picks.
  2. The system sign-in sheet opens OpenAI's page. The request asks for your identity and for plan usage. It uses PKCE and no secret, so the public repo holds nothing sensitive.
  3. OpenAI registers this install, sends the browser back to the listener, and the module exchanges the code for tokens.
  4. The module checks the identity token the way OpenAI's docs require: its signature against OpenAI's published keys, its issuer, its audience against the client ID OpenAI issued, its expiry, and the one-time value saved for this attempt.
  5. The module stores the tokens and the issued client ID as one Keychain item, kept per ChatGPT account, and reuses that client ID for later sign-ins to the same account. One refresh runs at a time, because each refresh retires the old refresh token.
  6. The coach is on only when the granted scope includes plan usage. If it does not, the app says the plan does not allow it and names the plans OpenAI lists.
  7. A ChatGPT sign-in renews itself while you use the coach. After 30 days without use it lapses, and you tap Continue with ChatGPT again.
  8. Sign out deletes the tokens and tells OpenAI to revoke them. It keeps the client ID for that account, as the docs say.

The port is not a straight copy. Your interval tracker checks the identity token's claims but not its signature, and it discards the client ID on sign out. C1 follows the docs on both.

ChatGPT's help page lists Go, Plus, Pro and Business as plans with this feature (Sign in with ChatGPT). OpenAI's developer quickstart lists only Plus and Pro. A Free account cannot use the coach. Everything else in the app works without ChatGPT.

The coach

  • Requests go from the phone to POST https://api.openai.com/v1/responses. OpenAI's preview rules for plan usage set the request shape:
    • Every request streams and sets store: false.
    • Instructions go in instructions. A system message is refused.
    • Function tools go in a namespace or as additional_tools input items.
    • previous_response_id, temperature and max_output_tokens are not allowed. The phone sends the whole chat with every turn.
    • A tool OpenAI does not support returns subscription_sharing_unsupported_capability, and the app shows that as an error.
  • Chats are kept on the phone in a coach_message table. They are part of export and never sync to the server. A chat longer than the model accepts keeps its most recent turns.
  • The coach answers from your data through tools that run on the phone against the local database. Read tools list workouts, exercise history, records, routines and measurements.
  • Write tools create a proposal. You see the routine or program as a preview, and you tap Apply. Undo removes it.
  • Each answer shows which of your data the coach read.
  • If plan usage refuses function tools, the coach falls back to the interval tracker's method. The app sends a summary of the relevant data in the request and asks for an answer in a fixed JSON format. C2 records which method shipped.
  • When the plan's limit is reached, OpenAI returns a specific error. The app stops sending and points you to ChatGPT's usage settings. svett never switches to another way of paying. ChatGPT's own usage settings may let an app spend your ChatGPT credits after the plan limit, and that choice is yours in ChatGPT.
  • The tool definitions live in one shared package. The connector in phase 7 uses the same definitions, so the coach in the app and an assistant outside it can do the same things.

Accounts, from phase 6

Until phase 6 there is no account. Continue with ChatGPT only turns the coach on. From phase 6 an account lets you sync and use the feed.

  • The sign-in screen has two choices: Continue with ChatGPT and Continue with email.
  • Clerk keeps the session. The server checks Clerk's token on every request.
  • Continue with ChatGPT also asks for a six-digit email code when it signs you in to your svett account. The ChatGPT sign-in gives the app your verified email address, and the app fills it in for you.
  • On Clerk's free plan, a sign-in lasts 7 days. After that, the app asks for a new email code before it syncs again. Logging and everything on the phone keep working meanwhile. Clerk Pro, at $25 a month or $20 a month billed yearly, allows longer sessions. The default is the free plan with a weekly code. The choice is yours before phase 6.

Whose data is on the phone.

  • Before any account exists, your data lives in one local database with no owner.
  • The first time you sign in, the app asks once whether to move that data into the account. If you say yes, the database becomes that account's. If you say no, the account starts empty, and the data without an owner stays on the phone. You can open it again after you sign out.
  • Signing out closes that database and keeps it on the phone. It opens again only for the same account.
  • Signing in as someone else opens a separate, empty database. Nothing from the first account is read or uploaded.

Why the code is there. OpenAI registers an open-source app on the phone, separately for each ChatGPT user, and issues it a client ID there. svett has no fixed client ID that its server could check. So the server cannot tell a ChatGPT identity token made for svett from one made for some other app you signed in to. Without a second check, that other app could sign in to svett as you. The email code closes that gap. OpenAI's interest form, a waitlist meant for commercial and hosted apps, might lead to a fixed client ID. If it does, the code step could go away.

Sync, from phase 6

  • Each change the phone makes gets its own ID and a timestamp from a hybrid logical clock. That clock orders changes across devices even when their wall clocks differ a little.
  • The phone keeps unsent changes in a queue and sends them when it has a connection. It removes a change from the queue only after the server confirms it.
  • The server remembers the ID of every change it applied. A change sent twice is applied once.
  • If two devices change the same row, the change with the later timestamp wins. If the timestamps are equal, the change with the higher change ID wins. Arrival order does not matter, so a retried old change cannot overwrite a newer one. The server rejects a timestamp more than a few minutes in the future. The phone then tells you its clock is wrong and holds the change until the clock is fixed.
  • Sets are separate rows. Two devices that log different sets in one workout both keep their sets.
  • The server gives every applied change a number that only goes up. The phone stores the last number it has fully saved, and asks for everything after it.
  • Deleting an activity deletes its exercises, sets and route with it. A later edit to one of those from another device is dropped. Undo is a restore with a newer timestamp, and it brings the activity back with what it had.
  • Sync covers one person's own devices. Other people's posts are read from the server and are never stored as your data.

Privacy

  • Each activity has an audience: everyone, followers, or only you. A setting holds your default for new activities, and it starts at only you. You can change it per activity.
  • Everything logged before you have an account, and everything imported, is only you. Moving your data into a new account keeps every audience as it was. Nothing becomes visible to anyone until you change it.
  • Each activity can hide fields: weight lifted, heart rate, start time, calories and pace.
  • A cardio route can hide its first and last stretch, so a map does not show where you live.
  • A private profile means you approve each follower.
  • Body measurements never appear in the feed.
  • What an assistant may read is a separate permission. Granting it changes nothing about what followers see.

The connector for ChatGPT, phase 7

The server exposes the shared tools through the Model Context Protocol at a public HTTPS address, with OAuth sign-in to your svett account. Clerk is the default sign-in service for it, acting as the OAuth provider ChatGPT talks to. If Clerk's plan does not cover that, or its sign-ins lapse after 7 days, the server runs its own OAuth on top of the svett account instead. X1 checks which, and you know before you choose a Clerk plan. Version 1 supports one way to connect, and it is the one OpenAI documents for a private server.

  1. On chatgpt.com, open Plugins, choose Add custom MCP server, and enter svett's address.
  2. Sign in to svett and approve read access, write access, or both.
  3. Ask ChatGPT about your training. ChatGPT may ask you before it writes. Either way, a write arrives in svett as a proposal that you apply in the app.
  • The Connected apps screen lists each connection, what it may do, and when it last read your data. Revoke cuts it off at once.
  • OpenAI says account and workspace policies decide who may add a custom server. Its docs do not list the plans, and they do not say whether the ChatGPT iPhone app can add or use one. X1 finds out with your account and records the answer.
  • A listing in ChatGPT's public directory would let anyone add svett in one tap. It needs a verified publisher, a privacy policy, terms, a support page and OpenAI's review. That is outside version 1.
  • Other assistants that speak the same protocol may work. Version 1 tests ChatGPT only.

Releases and AltStore

  1. A merge to main starts the release job on GitHub's own macOS runner, which is free for public repos. Your interval tracker uses the same pipeline. svett adds the ad hoc signing described below.
  2. The job builds a Release .ipa signed ad hoc with its entitlements file, with no Apple certificate. Then it creates a GitHub release and updates altstore.json on the latest release.
  3. AltStore refuses to install an app whose permissions differ from the ones the source lists. Expo adds permission keys on its own, and later phases add location and Health. So the job reads the permissions out of the built app and writes them into altstore.json.
  4. You add one source address in AltStore, once. AltStore then offers each new version.
  5. The version is the major and minor number plus the commit count, for example 0.3.41.

With a free Apple account, AltStore must refresh the app every 7 days. Your data stays on the phone across refreshes and updates.

How repeats and Undo work.

  • A Hevy file has no workout ID. A workout's identity there is its start time. Its title, exercises and sets are content. A row in a svett file has its own ID. D2 confirms the file's columns against your real export, including whether its times carry a time zone. The match against Apple Health in K2 depends on it.
  • Importing a workout that is already here and unchanged does nothing.
  • If the source workout changed since the last import, the preview lists it. A renamed workout counts as changed, not as new. You choose to keep yours or take the new one. The default keeps yours.
  • If a workout in the file has a new start time but the same exercises and sets as one already here, or two workouts in the file share a start time, the preview shows it as a possible duplicate and you choose. If you keep both workouts that share a start time, the second one's identity adds its position in the file, so the two get different IDs.
  • Taking the new one keeps the version it replaces.
  • Undo removes the workouts an import added and puts back the versions it replaced. A workout you edited after the import is listed and left as it is, unless you choose to undo it too.
  • Apple Health imports in K2 follow the same rules, with the Health workout ID as the identity.
  • One workout can arrive from two sources, such as Hevy and Apple Health. If a new workout overlaps the time of one from another source, the preview shows it as a possible duplicate. Linking keeps one activity that records both source identities, so neither source imports it again.

9. How each pull request is checked and reviewed

  1. Build. One agent owns the pull request on its own branch on rena-devbox. rena-devbook runs the native builds and the simulator for it. I read its whole diff myself.
  2. Automated checks. Lint, type checks and unit tests pass locally and on GitHub. Logic lives in packages/core, where tests run in seconds without a simulator.
  3. Run it for real. A saved script drives the app in the iPhone 16 Pro Max simulator and takes a screenshot at each step of the proof. Anyone can rerun the script. Passing tests alone never count as done.
  4. Sol loop. GPT Sol reviews the diff. I fix real findings with the smallest change and decline the rest with a reason. Up to three rounds.
  5. Council. Claude Opus and GPT Sol each review the pull request and score it out of 10. They see the code, the test results and the screenshots.
  6. Merge at 9. Both scores must be 9 or higher. Below that, I fix and ask for a fresh round. The scores for every round go in the pull request description.
  7. Ship. The merge starts the release job, and AltStore offers the new version.
  • If a pull request stalls. After four council rounds without two scores of 9, I stop and bring it to you with both sides of the disagreement. I do not merge it.
  • Scope stays fixed. A reviewer's idea that is outside the pull request goes on a follow-up list in docs. It does not grow the pull request.
  • At most two pull requests are open at once. Each has its own working copy and Metro port on rena-devbox. They take turns on the one simulator. The 15 GB of memory on rena-devbox is the other limit.
  • A decision log in docs records each choice made without you, and each review score.
